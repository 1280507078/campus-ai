## 1. 为什么 Agent 非测不可

普通接口的 bug 一眼就能看出来：返回 500、字段缺失、页面白屏。
**Agent 的 bug 长得像正常答案。**

它会把「今天」猜成 2023-04-15、查出一个空课表、再排出一份格式完美、
和真实时间表毫无关系的计划 —— 从输出上完全看不出错在哪（这条是真踩过的，
现在系统提示词第 ⑧ 条就是为了堵它）。同类还有：

- 把课上时间排成自习时间（「14:50-15:35 预习计算机组成原理」，
  而 14:50-15:35 正是这门课的上课时间）；
- 问「休学要什么材料」，返回一张作息表；
- 问手册里根本没有的事（校园卡补办），照着「毕业证明补办」的流程编一套。

这些东西靠人点几下是抓不住的，也抓不全。所以要有能**重复跑、能对比前后**的评测。

## 3. 两层跑法：先离线，再在线

```
python tools/eval_agent.py            # 离线：只跑 route_of，秒级，不花钱
python tools/eval_agent.py --live     # 在线：真跑 /api/planner/plan，一条 20~50 秒
```

**离线层**只验「这句话该走哪条路」。为什么值得单独一层：
路由判据一改就要重跑，而这个循环一天可能要转几十次 ——
真跑模型根本转不动（15 条要 7 分钟、要花钱）。

**在线层**只跑 `route == "plan"` 的 15 条。其余四条路是规则 / 本地逻辑，
不走模型，在线跑它们等于重复测离线已经测过的东西，只是把账单变长。

### 关键：路由与评测共用同一份判据

`route_of()` 在 `routers/planner.py` 里，**线上分派和评测脚本调的是同一个函数**。
如果评测自己另写一套判断，那测出来的就不是线上跑的那套规则 ——
数字再好看也没意义（这是「循环论证」的另一种形式）。

### 4.3 上一轮的三条失败（本轮已全部修掉）

上一轮如实留着的三条，根因是同一个：**这三类问题连五条路都不匹配，只能落 `plan`**，
而 `plan` 的入口就是「先把课表和空档查一遍」。

| 用例 | 原话 | 期望工具 | 上一轮实际 | 本轮实测 |
|------|------|----------|-----------|---------|
| X03 | 今天天气怎么样 | `get_weather` | + `get_timetable` + `find_free_slots`，**还生成了一份学习计划** | **2.5 s · 只调 `get_weather`** |
| X04 | 博文楼在哪 | `get_building_info` | 一个正确工具都没调，用课表数据凑答案 | **0.02 s · 只调 `get_building_info`** |
| X05 | 计算机组成原理是哪位老师 | `get_timetable` | + `find_free_slots` + `get_class_schedule` | **0.00 s · 只调 `get_timetable`** |
| X01 | 大学有几个楼 | 不该调工具 | 33.1 s，调了课表 + 空档两个工具 | **0.00 s · 0 次工具** |

**为什么提示词救不了**：上一轮试过在 system prompt 末尾加一条「寒暄/闲问不要调工具」，
**实测零效果** —— 7 条干扰题的多余调用率 100% → 100%，X05 还丢了本来调对的工具。
模型对「我在干什么」的理解来自整段提示词的角色设定（「你是规划 Agent，基于真实时间表生成计划」），
末尾一条禁令压不过它。

**真正的修法**：在 `route_of` 里加第六类 `quick`，判出来之后**只跑一个工具，
答案用模板拼**（`study_agent.quick_answer`），一整轮模型调用都不发生。
- 天气和楼名是**确定数据**，没有任何理由让它等 20 秒，更没有理由给模型编的机会
  （模型在「博文楼到底在南区还是北区」上有幻觉空间，`_norm_building` 查表则没有）；
- 「学校有几个楼」连工具都不用调 —— 楼名表是常量。

**判据里的一个坑**（留出集抓出来的）：「图书馆**怎么走**」要的是导航，
但「图书馆**几点开门**」问的是规定。两句只差一个字，所以 `_WHERE_Q` 后面挂了一个
动作负向断言（`在哪` 后面跟「看/打印/办/领…」就不算位置）。没有它，
「校历在哪看」「成绩单在哪打印」会被当成问路，然后答「教学楼表里没有校历」。

### 4.4 这次评测逼出来并修掉的三个真问题

**① 「你好」花掉 34 秒和 1 万 token**

`route_of` 的五条路都不匹配纯寒暄，只能落到 `plan`，于是被当成「要排计划」。
修法不是改提示词（试过，无效），而是**代码层短路**：
`planner.small_talk()` 用 `^…$` 全串匹配纯寒暄 / 道谢 / 应声，命中直接回一句，
**根本不进 Agent**。判据故意做得极窄 ——「你好，帮我排个计划」带着任务，照常进 Agent。

| | 修前 | 修后 |
|---|---|---|
| 你好 | 49.2 s · 2 次工具 · 9 k token | **0.03 s · 0 次工具** |
| 谢谢 | 29.1 s · 2 次工具 | **0.00 s · 0 次工具** |

**② 手册里没有的事，它会照别的文档编**

第一版的表现：问「校园卡丢了怎么补」，向量检索最高分 0.458 命中「毕业、学位证明书办理流程」
—— 语料里根本没有校园卡，模型就照着毕业证明的流程答。
单纯提阈值没用：真正该命中的「什么时候放寒假」只有 0.440，**比那条错命中还低**。

修法是 hybrid 检索（`services/qdrant.py: search_docs`）：
语义 ≥0.56 直接放行；0.40~0.56 必须有**字面二字词锚点**；<0.40 丢弃。
停用词里必须含**泛动作词**（申请 / 办理 / 流程 / 材料），否则「怎么申请奖学金」
会命中「缓考申请」。

更关键的是**拒答从机制上保证**：检索为空时 `ask_docs` **根本不调模型**，
直接给固定口径「手册里没有写 + 教务处 0591-83969194」。
让模型在空上下文里自由发挥，它一定会编出一套像模像样的流程 ——
这是 RAG 最典型的翻车方式，所以干脆不给它这个机会。

**③ 扩语料反而把「拒答」弄坏了 ——「同主题 ≠ 同动作」**

上一轮之后把语料从 14 篇扩到 29 篇（图书馆 / 后勤 / 信息化中心，见第 8 节）。
结果「校园卡丢了怎么补」从**正确的拒答**变成了**一本正经地编**：

> 校园卡丢失后，可以通过以下步骤进行补办：
> 1. 前往校园卡服务中心办理补卡手续。2. 凭有效证件（如学生证）和校园卡密码进行身份验证。
> 3. 服务中心工作人员将为您办理新卡，并可能需要您支付一定的补卡费用。
> 来源：《校园一卡通线上充值指南》

三句话没有一句是真的，而且它标了一个**看起来完全可信的出处** ——
这比答"不知道"糟糕得多。

**根因不是检索分数**：新语料里有《校园一卡通线上充值指南》，和问题共享「校园卡」三个字，
余弦 0.485 也够。问题在于**同主题不等于同动作** —— 片段讲"充值"，用户问"补办"。
提示词里「片段里没有的不要写」拦不住它：片段里确实有「校园卡」，模型判断不了
"有校园卡 ≠ 有补办"。

**修法是把这个判断从模型手里拿走**：`_missing_actions()` 抽出用户问的动作词
（补办/挂失/报修/充值/找回/丢了…），逐个检查它们在检索片段里有没有出现；
没出现的，**直接写进提示词**：

```
⚠️ 检索结果里没有用户问的这个操作：「丢了」在所有片段里一次都没出现。
   这说明检索到的是同主题的另一件事……直接说「学校手册里没有写这条流程」。
```

修复后同一个问题的回答：

> 学校手册里没有写这条流程。建议联系教务处（0591-83969194）或辅导员咨询补办校园卡的具体流程。

> ⚠️ 一个反向守卫：「宿舍坏了怎么**报修**」的正确解法就是报修指南，
> 所以"报修"不能一律判成缺失 —— 判的是**片段里有没有这个动作**，不是**问题里有没有**。
> `tools/test_rag_docs.py` 的 G 段同时钉住了正反两侧。

## 5. 一次踩到的「评测本身坏了」

在线评测跑了三轮，数字一直不动 —— 提示词改了也没变化。
排查发现：`eval_agent.py --live` **不会自己起服务**，它只往
`--base http://127.0.0.1:8000` 发请求；而 8000 上是我几小时前
`python main.py` 起的**旧进程**（没有 `--reload`），代码改了它毫无感知。

结论：**离线评测能自证（进程内 import），在线评测不能 —— 它会静默测旧代码。**
以后跑在线评测前，先确认服务是新起的：

```bash
netstat -ano | grep ":8000.*LISTENING"     # 有旧进程就先停掉
cd backend && PORT=8000 python main.py     # 再起一份
curl --noproxy '*' http://127.0.0.1:8000/api/ping
```

改完再跑，数字才有意义（本文所有在线数字都是重启后的）。

### 无障碍这一轮修了什么

axe-core 首扫 13 处 serious，4 类问题：

1. **顶栏账号链接的 `aria-label` 与可见文字对不上**（10 处 / 9 页）。
   可见文字是「我的 / 昵称」，但 `aria-label="账号设置"` ——
   读屏用户听到的名字和眼睛看到的不是一回事。改成
   `aria-label="账号设置：我的 <昵称>"`，两种窄屏形态都覆盖到。
2. **品牌色当小字用，对比度不够**（`#6366f1` 在浅底 3.99:1、深底 3.11:1，要求 4.5:1）。
   `--brand` 同时当底色和边框用，不能整体改深，所以拆出 `--brand-text`
   （浅色 `#4f46e5` / 深色 `#a5b4fc`）**只给文字用**。
3. **课表时间列的次要时刻用了 `opacity:.5`**，10px 字降到 2.05:1，灰到几乎看不见。
   改用已经校过对比度的 `--ink-faint`，层次靠字号区分。
4. **危险区标题的红字 3.57:1** → 拆出 `--danger-text`（浅色 `#c62828` / 深色 `#ff8a80`）。
5. 另有一页 `<meta viewport>` 写了 `user-scalable=no`，把缩放禁掉了（moderate），已去掉。

## 7. 已知局限（不藏着）

1. **样本小**：在线只跑 15 条，模型有随机性，单条结论不能当统计结论。
   工具指标只有 6 条有标注 —— 现在 6/6 全对，但**6 条不足以证明"工具永不错"**，
   只能说这几类判据确实钉住了。
2. **延迟是最大短板**：真要排表时 P50 24.8 秒、P95 49 秒。一次对话 3 轮模型调用，
   每一轮都要等模型；换更快的模型或减少轮数都能降，但都会牺牲计划质量。
   （`quick` 类不走模型，天气 2.5 秒、位置 0.02 秒，不受这个限制。）
3. **语料还有明显缺口**：29 篇覆盖了教务 / 图书馆 / 后勤 / 校园网，
   但**校园卡补办、宿舍水电、奖学金评定、医保报销**这些学生真会问的仍然没有官方公开文档
   —— 现在只能是拒答（诚实，但确实答不出）。
4. **没有真人评分**：目前只有「有没有答对 / 调没调对工具」这类机械指标，
   没有「这份计划好不好用」的主观评价。要做得再实一点，需要找几个真学生按
   「照着做了一周，哪些条目没法执行」打分。
5. **评测集是我自己造的**：句子风格贴近真实提问（含口语、省略、错误记法），
   但终究不是从真实用户日志里捞的 —— 覆盖不到「用户根本不会这么问」的盲区。
6. **CI 没在 GitHub 上真跑过**：本仓库当前不是 git 仓库（内网单机开发），
   `.github/workflows/ci.yml` 里的每一步都在本机按同样命令手工跑过、
   核对过输出，但没有在 Actions 上验证过。
